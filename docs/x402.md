# x402 paid-session API

x402 is an optional accountless API that sells time-limited browser sessions.
It is disabled by default and isolated from the normal client-ID/client-secret
API. Challenges include the MPP route-binding extension, so `mppx` and future
Cloudflare Virtual Wallet clients can pay through MPP's x402 compatibility
path without replacing Popcorn's settlement ledger or reconciliation worker.

Application developers should use [the x402 client guide](x402-client.md) for
wallet setup, payment handling, LiveView/CDP connection, extension, and
termination. This page is for deployment operators.

## Isolation model

Configure exactly one enabled region as `x402Only: true` and set
`controlPlane.x402.regionName` to it. Credentialed `/v1/sessions` requests never
select an x402-only region, and x402 requests never fall back to a normal
region.

This separation limits payment, route-bound automation, capacity, and incident
response to a dedicated browser pool.

## Public routes

| Action | Route | Payment/authentication |
| --- | --- | --- |
| Create | `POST /v1/x402/sessions` | x402 payment challenge |
| Extend | `POST /v1/x402/sessions/:id/extend` | capability plus new payment |
| Status | `GET /v1/x402/sessions/:id` | possession capability |
| Terminate | `DELETE /v1/x402/sessions/:id` | possession capability; no refund |

The public session ID and every returned URL are capabilities. Redact them as
credentials.

## Minimum configuration

```yaml
controlPlane:
  regions:
    - name: x402-us-central1
      clusterName: popcorn-x402-us
      poolManagerUrl: http://pool-manager.popcorn-x402.svc.cluster.local
      publicGatewayUrl: https://x402-browser.example.com
      enabled: true
      x402Only: true
      poolManagerAuth:
        secretName: pool-manager-x402-service-auth
        secretKey: POOL_MANAGER_SERVICE_AUTH_TOKEN
  x402:
    enabled: true
    regionName: x402-us-central1
    network: "eip155:<chain-id>"
    testnet: true
    publicBaseUrl: https://x402-api.example.com
    payTo: "0x..."
    blockSeconds: 300
    pricePerBlockAtomic: 10000
    paymentAssetAddress: "0x..."
    paymentAssetName: USDC
    paymentAssetVersion: "2"
    facilitatorUrl: https://<facilitator>
    facilitatorAuthMode: none
    secretName: control-plane-x402-secret
```

Validate the network, payee, asset address/name/version, atomic price, purchased
duration, facilitator, and public origin independently. Start on a test network
and use a dedicated capacity ceiling.

## Secrets

The `control-plane-x402-secret` uses configurable key names. The defaults are:

| Key | Required |
| --- | --- |
| `X402_SERVER_SECRET` | yes |
| `X402_BASE_RPC_URL` | yes |
| `CDP_API_KEY_ID` | only for Coinbase CDP facilitator auth |
| `CDP_API_KEY_SECRET` | only for Coinbase CDP facilitator auth |
| `X402_FACILITATOR_AUTH_HEADERS` | only for static header auth |

Never store payer private keys in Popcorn. Callers sign payments in their own
wallet or custody boundary.

## Create lifecycle

1. Caller sends `POST /v1/x402/sessions` with a unique `Idempotency-Key`.
2. Control plane returns `402 Payment Required`, x402 v2 payment requirements,
   and an MPP-compatible route binding.
3. Caller validates the offer against independently configured expectations.
4. Caller signs and repeats the identical request with the same idempotency key
   and `PAYMENT-SIGNATURE`.
5. Control plane settles payment, allocates only in the x402 region, stores
   durable intent/state, and returns capabilities.

A successful response can contain:

- public capability `sessionId` and `sessionUrl`;
- automation-scoped `connectUrl`;
- restricted `liveViewUrl`, `vncUrl`, and `vncWsUrl`;
- `expiresAt` and paid-duration fields;
- payment transaction identity and asset metadata.

It deliberately omits `cdpInternalUrl` and generic extension `apiUrl`.

## Extension and stable capabilities

To purchase more time:

```http
POST /v1/x402/sessions/:id/extend
Idempotency-Key: <new unique key>
Content-Type: application/json

{ "blocks": 2 }
```

The first response is another 402 challenge. Repeat the identical request with
the signed payment. Existing browser capability URLs remain stable while the
server extends the route-bound access deadline.

## Idempotency and retries

- Reuse the same idempotency key, path, body, and payment signature after an
  ambiguous timeout.
- Never reuse one key for a different body or action.
- Do not create a second payment merely because the first response was lost.
- A completed replay still requires proof of the original payment; the key
  alone must not reveal the capability.
- Honor `Retry-After` for overload/conflict responses when present.

## Production controls

- Put the x402 API behind TLS, rate limiting, and external abuse controls.
- Keep x402 Postgres, Redis, pool manager, and RPC credentials private.
- Cap `maxExtensionBlocks`, `maxPaidBlocks`, and regional browser capacity.
- Alert on challenge, settlement, allocation, extension, reconciliation, and
  cleanup failures separately.
- Reconcile ambiguous settlements before accepting or retrying payment.
- Terminate compromised capabilities; early termination does not refund time.
- Redact payment signatures, capability IDs/URLs, RPC credentials, and wallet
  material from logs.

## Pre-production acceptance

- [ ] Testnet create challenge matches expected payee, asset, amount, network,
      and duration.
- [ ] Paid retry creates exactly one session.
- [ ] Replaying the paid request is idempotent.
- [ ] Extension charges the expected multiple and preserves URLs.
- [ ] Status and termination require possession of the capability.
- [ ] Credentialed clients cannot select the x402 region.
- [ ] x402 cannot fall back to a credentialed region.
- [ ] Rate limiting and capacity exhaustion fail safely.
- [ ] Crash/timeout reconciliation is exercised.
- [ ] Logs contain no payment signatures or capabilities.

For ordinary integrations, use the [credentialed API](reference.md#credentialed-client-api).
