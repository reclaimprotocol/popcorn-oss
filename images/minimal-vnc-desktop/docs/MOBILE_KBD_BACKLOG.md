### [H/S] Re-raise keyboard on tap of the already-focused remote field (fixes permanent Android wedge)

- **Problem:** After ANY local dismiss that doesn't blur the remote (Android back-button/swipe-down, watchdog force-dismiss, miss-tap dismiss), the remote field stays focused with an unchanged focusKey. A re-tap on that field classifies 'hit', but handleTap's Android branch defers to applySignal, and applySignal's recovery requires isNewField (focusKey CHANGE, kbd-autofocus.js:1075). The already-focused field never emits a new focusin (content.js dedupes), so on Android the keyboard can NEVER be re-raised on the same field — the single most common flow (back-dismiss, then tap back into the field) is permanently wedged. On iOS it works only via the accepted-flicker in-gesture raise.
- **Hack:** In handleTap's 'hit' branch (kbd-autofocus.js:866), before deferring: if remoteFocusKey is non-null (remote authoritatively says an editable is focused) AND the tap falls inside currentRect (same 6px pad as hitTest), treat it as a confirmed re-focus tap and call raiseKeyboard('tap-refocus') immediately on BOTH platforms — in-gesture, so iOS-legal, and no armDismiss needed since editable:true is already the cached authoritative state.
- **Why it helps:** Zero-RTT: uses only cached authoritative state, so it works identically at 5s RTT. Closes the most-hit lifecycle dead end (back-button dismiss then retap) with no false-pop risk — the remote itself reported this exact rect as its focused editable field.
- **Implementation:** kbd-autofocus.js handleTap(): inside `if (hit === 'hit')`, add `const m = screenToRemote(x, y); if (remoteFocusKey && currentRect && m && pointInRect(m.rx, m.ry, currentRect, 6)) { const wasActive = keyboardActive; raiseKeyboard('tap-refocus'); if (!wasActive && isIOS) armDismiss(); return; }` before the existing iOS/Android split. Factor the rect-containment test out of hitTest into a small pointInRect helper.
- **Risk:** currentRect can be scroll-stale, so a tap on where the focused field USED to be could raise spuriously; mitigate by requiring the last /kbd message to be recent (<3s) or accept — worst case is one extra raise on an editable-focused page, dismissed by the next signal.

### [H/S] Make the 1500ms authoritative-recovery window RTT-adaptive like the dismiss timer

- **Problem:** kbd-autofocus.js:1075 hardcodes `(nowMs() - lastTapAt) < 1500` while the dismiss timer already adapts via emaLatency up to 5000ms. On a 3G link with 2-4s tap-to-confirm latency, every 'unknown' tap and every Android 'hit' tap gets its editable:true confirmation AFTER the window, so the keyboard silently never raises — the exact network this system targets.
- **Hack:** Replace the literal 1500 with a recoveryWindow() function using the same EMA: `Math.max(1500, Math.min(8000, emaLatency * 2.5 + 400))` (default 1500 when unlearned). Keep the EMA learning as-is — it already samples tap->confirm latency at line 1057-1061.
- **Why it helps:** This is THE high-latency-3G fix in this file: the recovery raise is the only path for cross-origin/closed-shadow/cold-cache fields and for all Android 'hit' taps, and today it has a cliff at exactly 1.5s RTT. Idempotent and absolute — a late confirm just raises a bit later, matching native 'slow page' feel instead of dead taps.
- **Implementation:** kbd-autofocus.js: add `function recoveryWindow() { if (emaLatency <= 0) return 1500; return Math.max(1500, Math.min(8000, emaLatency * 2.5 + 400)); }` next to dismissDelay() (~line 904), and use it at line 1075. Note EMA only learns from confirmed taps, so also seed it pessimistically: on the first tap whose confirm arrives between 1500-8000ms, the isNewField EMA-learning branch at 1057 already records it — that works because EMA learning is not gated on the raise happening.
- **Risk:** A raise can now fire up to 8s after a tap, which could surprise a user who tapped and moved on; acceptable and bounded — a genuine editable:true for a NEW focusKey within 8s of a tap is near-certainly caused by that tap.

### [H/S] Grace-debounce editable:false so transient remote blur→focus doesn't dismiss (and lose) the keyboard

- **Problem:** applySignal's else-branch (kbd-autofocus.js:1085) calls dismissKeyboard() the instant editable:false arrives. Pages that blur field A and focus field B asynchronously (custom widgets, validation-on-blur, framework re-renders) produce a transient false between two trues. Content.js's one-tick focusout defer only covers synchronous refocus. Result: keyboard dismisses, then the follow-up editable:true triggers raiseKeyboard('recovery') OUTSIDE the gesture — which flickers on Android and silently fails on iOS (the code's own comment says iOS only raises in-gesture). On 3G the false and true can arrive seconds apart, guaranteeing the flicker/loss.
- **Hack:** Never act on editable:false immediately while keyboardActive: schedule pendingFalseDismiss = setTimeout(dismissKeyboard, ~350ms) and cancel it if any editable:true arrives first. Immediate state (currentRect=null etc.) can still update; only the user-visible dismiss is debounced.
- **Why it helps:** Absorbs the blur→async-focus transition entirely on field-to-field moves, so the keyboard stays up across remote focus churn — the native behavior. Especially valuable on iOS where a wrongly-dismissed keyboard is unrecoverable without another tap, and on high-RTT links where the false/true pair straddles seconds.
- **Implementation:** kbd-autofocus.js applySignal(): in the else-branch, replace `if (keyboardActive) dismissKeyboard();` with a 350ms cancelable timer (clear currentRect/recon state immediately as today). In the editable:true branch, clearTimeout(pendingFalseDismiss) alongside the existing clearDismiss(). Keep instant dismissal when !keyboardActive (nothing to protect).
- **Risk:** Dismiss latency grows by ≤350ms when the remote genuinely blurred (e.g. form submitted) — imperceptible next to the RTT already in the loop. Do NOT scale this window by emaLatency or a slow link makes legitimate dismisses feel sticky.

### [H/S] Client-side /kbd staleness watchdog: force-reconnect when no message arrives within 2x publisher keepalive

- **Problem:** The /kbd viewer socket has zero client-side liveness. The publisher keepalive guarantees a message every ≤20s while healthy (background.js KBD_PING_MS=20000), and the server pings every 30s — but a half-open connection after a wifi→cellular switch or NAT rebind leaves the browser WS object 'open' with no data for minutes. During that window every focus signal is lost: taps hit stale rects, Android 'hit' and 'unknown' taps never get their editable:true, dismiss signals never arrive. The stuck-keyboard watchdog only covers dismissal, not the dead-signal case.
- **Hack:** Track lastKbdMsgAt on every onmessage (including deduped ones); a 15s interval checks `nowMs() - lastKbdMsgAt > 45000` (2x keepalive + slack) and if exceeded calls sock.close() — the existing onDown handler then reconnects with backoff, and the hub's add() resync replays lastState so the client is instantly current again.
- **Why it helps:** On lossy mobile links, half-open sockets are the norm, not the exception. Recovery drops from 'until TCP gives up' (often 5-15 min) to ≤45s, and reconnect resync is already idempotent/absolute so the repair is free. Complements rather than duplicates the server's 70s read deadline (which only cleans up the SERVER side).
- **Implementation:** kbd-autofocus.js: in connectSignal(), stamp `lastKbdMsgAt = nowMs()` in onopen and onmessage; start one module-level setInterval(15s) (only while a socket exists) that closes the socket when stale. Guard against the interval firing during the backoff gap (only check when sock !== null).
- **Risk:** Low. Worst case is an unnecessary reconnect on a healthy-but-idle path, which the hub resync makes invisible. Requires the publisher keepalive to actually reach viewers — it does today (hub relays every publisher frame).

### [H/S] Reset backoff and reconnect all channels immediately on online / pageshow / visible / RFB-attach

- **Problem:** All three client channels wait out their current backoff blindly: /kbd is at up to 10s backoff, /input retries at a fixed 1s, and none of them (nor liveview's RFB loop) listens to `online`, `pageshow` (bfcache restore), or `visibilitychange`. After a network drop + restore, or an iOS Safari bfcache resume where sockets died without close events, the keyboard layer can sit dark for ~10s after the link is demonstrably back — and a successful RFB reconnect (proof of connectivity) doesn't kick /kbd at all.
- **Hack:** Central 'network probably back' hook: on window 'online', document visibilitychange→visible, pageshow (event.persisted), and inside PopcornKbd.attach(): (1) reset wsBackoff to WS_BACKOFF_MIN, (2) if sock is null or readyState CLOSED, connectSignal() now; same for inputSock; (3) run one immediate watchdog check so a keyboard that died while hidden is cleaned up instantly instead of after throttled-interval delays.
- **Why it helps:** Mobile radios flap constantly on 3G; event-driven reconnect converts worst-case 10s dead windows into ~0. bfcache restores (extremely common on iOS back-navigation) currently leave sockets in undefined states with throttled timers — pageshow is the only reliable resume signal.
- **Implementation:** kbd-autofocus.js: add kickChannels() that resets wsBackoff, calls connectSignal()/connectInput() when down; register window.addEventListener('online'|'pageshow') and document visibilitychange in setup(); call kickChannels() from PopcornKbd.attach(). Guard connectSignal/connectInput against double-connect (check sock readyState CONNECTING/OPEN before dialing — connectSignal currently has no such guard, so a kick during an in-flight scheduleReconnect timer could create two sockets; add a `connecting` flag or cancel the pending timer).
- **Risk:** Low, but the double-connect guard is mandatory — today connectSignal unconditionally dials, and two live sockets would double-apply signals (idempotent, but wasteful) and fight over `sock`.

### [H/S] Guard the iOS input/beforeinput fallback with composition state (iOS CJK is currently broken)

- **Problem:** On iOS (hidden <input> path), Chinese Pinyin/Zhuyin, Japanese Kana/Romaji, and Korean keyboards all use marked-text composition. beforeinput fires with inputType insertCompositionText (plus iOS-specific insertFromComposition/deleteCompositionText), which onProxyBeforeInput (kbd-autofocus.js:157-171) does not handle, so the unprevented input event reaches the iOS fallback (lines 230-232) which sendText()s the FULL partial composing string on every update AND sets proxy.value='' mid-composition — cancelling the IME — then compositionend (line 291) sends e.data again, double-committing whatever survived.
- **Hack:** In onProxyInput's non-Android branch, return early when isComposing || e.isComposing || (e.inputType||'').startsWith('insertComposition') || e.inputType==='insertFromComposition' || e.inputType==='deleteCompositionText'; never touch proxy.value while composing; let onCompositionEnd remain the single commit point (it already clears value).
- **Why it helps:** Restores the entire composition-IME family on iOS/iPadOS (Pinyin, Wubi via 3rd-party keyboards, Kana-Kanji with candidate selection, Hangul syllables). Over a 3s-RTT 3G link this also collapses per-composition traffic from one keysym burst per marked-text update to exactly one commit burst — the remote echo delay stops mattering because nothing speculative is sent.
- **Implementation:** kbd-autofocus.js onProxyInput (~line 230): add the composition guard before 'if (currentValue) sendText(currentValue)'. In onProxyBeforeInput iOS section, explicitly no-op (no preventDefault, no value clear) for insertCompositionText/insertFromComposition/deleteCompositionText. Keep onCompositionEnd unchanged as the commit.
- **Risk:** low — pure client-side; behavior for non-composing iOS input (insertText path) untouched

### [H/S] isComposing/keyCode-229 guard on all special-key keydown handlers

- **Problem:** Pressing Enter to commit a Japanese/Chinese conversion candidate, or Escape to close a candidate window, fires keydown with key='Enter'/'Escape' and event.isComposing=true. onProxyKeyDown (kbd-autofocus.js:235-272) and onECKeyDown (343-362) have no composition check: Enter is preventDefault'ed and forwarded as a remote Enter keysym (submitting the remote form mid-composition), Tab tabs away, and Escape locally toggles the keyboard, killing the composition.
- **Hack:** First line of both keydown handlers: if (e.isComposing || e.keyCode === 229) return; (do not preventDefault, do not forward).
- **Why it helps:** Enter-to-commit is the core interaction of every kana-kanji and pinyin conversion flow; today each commit risks a remote form submit. On high-latency links the user cannot even see the accidental submit until seconds later, by which point they have typed more into a navigated-away page.
- **Implementation:** kbd-autofocus.js: add the guard at the top of onProxyKeyDown (line 236) and onECKeyDown (line 344). keyCode 229 covers Android keyboards that report composition keys that way.
- **Risk:** low

### [H/S] Derive composing state from event.isComposing, not only compositionstart tracking

- **Problem:** isComposing is set solely by the compositionstart listener (kbd-autofocus.js:286). The Android branch then takes the !isComposing paths at lines 209/215/222 and sets proxy.value='' mid-composition — which cancels the CJK composition.

- **Why it helps:** Removes the IME-cancellation failure mode for Samsung Keyboard/Sogou/Baidu IMEs whose composition lifecycle events are unreliable — full coverage of real-world Chinese keyboards, not just Gboard.
- **Implementation:** kbd-autofocus.js onProxyInput Android branch: compute const composing = isComposing || e.isComposing || inputType === 'insertCompositionText'; use it in the three proxy.value-reset guards; mirror in onECTextUpdate's filterAutoSpace gate.
- **Risk:** low

### [H/S] Queue text sent while RFB is disconnected and flush on reattach

- **Problem:** sendText/sendSpecialKey silently drop when rfb is null or sendKey throws (kbd-autofocus.js:57-79 catch(_){}). ### [REJECTED] Server-side H.264 into noVNC's open-h264/WebCodecs decoder (temporal codec for 3G motion)

- **The idea (kept for the record):** TigerVNC only emits intraframe Tight/JPEG, so a scroll re-sends whole tiles and full-viewport updates are seconds-long on 3G. noVNC 1.6 already ships an H.264 decoder (encoding 50, activates when `WebCodecs` exists), so the plan was to feed H.264 from an `ffmpeg x11grab -> libx264` sidecar and make the Go proxy an RFB-aware MITM that swaps TigerVNC's pixel rects for encoding-50 `[length][flags][Annex-B]` rects — inter-frame, so a scroll becomes motion vectors instead of a full re-encode. The decoder contract was verified from noVNC v1.6.0 source and an on-device decode harness was built (published as an Artifact). Client half proven-feasible; server half never built.
- **Why REJECTED (transport, not codec):** the bytes/frame win is real but assumes a *clean* pipe, and 3G is not clean. H.264's value is frame-to-frame dependency, which is a liability on a lossy/variable link: (1) any lost packet corrupts the reference chain until the next big IDR — a visible freeze/smear on every blip, where Tight's independent rects recover the instant bytes flow; (2) **RFB runs over TCP (wss tunnel)**, so a delayed segment head-of-line-blocks everything behind it, and H.264's dependency chain means the decoder can't progress until the retransmit lands — H.264-over-TCP compounds TCP's worst weakness instead of hiding it; (3) no congestion control, so a fixed x264 bitrate either overshoots (stalls) or wastes quality on a swinging 3G downlink, whereas Tight's per-update quality knob is trivially adaptable — and already is (`kbd/quality.js`). Mobile reconnects also force an IDR every time → keyframe storms.
- **The one mitigation, and why it's insufficient:** x264 intra-refresh (spread I-macroblocks, no big IDR spikes) fixes the keyframe-storm/recovery problem but does *nothing* for the TCP head-of-line blocking, which is baked into RFB-over-websocket. KasmVNC's video modes ride the same TCP/websocket and inherit the same HoL problem, so a Kasm swap wouldn't help here either.
- **What "best for 3G motion" actually is:** H.264 over a *loss-tolerant* transport — WebRTC/RTP over UDP with congestion control and the ability to skip a frame instead of stalling (cloud-gaming stacks: Selkies-GStreamer, neko). That's a separate, much larger project (new transport, not an encoding swap), and only worth it if motion performance becomes a hard requirement. For a read-and-type browser portal it likely isn't.
- **Direction instead:** stay on Tight and keep exploiting its independence on lossy links — adaptive JPEG quality (`kbd/quality.js`) and optimistic scroll prediction (shipped, commit 3b1444c) are the right lane. See also `docs/MOBILE_KBD_SMOOTHNESS_PLAN.md`, which independently found H.264-preference is a no-op on this TigerVNC/RFB stack.

### [M/M] Split /kbd into a slim focus/len message + bulk rects message

- **Problem:** Every /kbd message carries ALL editable rects (up to 60 rects ~2KB) because rects ride on every report. - **Hack:** Add a message kind field: {k:'focus', editable, focusKey, rect, hints, sync, vw, vh} sent immediately on focus/input changes (couple hundred bytes), and {k:'rects', rects, vw, vh} sent on the existing 250ms scroll/resize throttle and heartbeat. Directly shortens the recovery-raise and dismiss-timer paths that today can exceed the fixed 1500ms window on slow links.
- **Implementation:** content.js describe()/report(): emit two shapes; background.js mergeFrames: merge per-kind; keyboard.go: cache lastState per kind (map[string][]byte) and replay both in add(); kbd-autofocus.js applySignal: branch on msg.k with back-compat for the old combined shape.
